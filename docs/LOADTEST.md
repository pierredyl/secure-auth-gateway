# Load testing

How to run a load test against the gateway and read what comes out.

One run measures four things at one fixed concurrency level: **throughput**,
**tail latency**, **error rate**, and **CPU saturation**. Concurrency is the
controlled variable — you run the same command several times at different levels
and compare the reports.

This document covers the run harness. For the flags on the Go generator itself,
see [`cmd/loadtest/README.md`](../cmd/loadtest/README.md). For the results of
past benchmarking, read the per-run reports in [`results/`](../results) — one
markdown file per run, generated by `cmd/loadreport`.

---

## Quick start

```bash
make loadtest CONCURRENCY=200
```

That brings the stack up if it is not running, drives 200 concurrent virtual
users at `GET /api/v1/health` for 30 seconds, samples CPU the whole time, and
writes `results/loadtest_200_<timestamp>.md`.

Two others worth knowing:

```bash
make help
```

```bash
make down
```


## Tunables

Override any of these on the command line. `make help` prints them at their
current values.

| Variable | Default | What it changes |
|---|---|---|
| `CONCURRENCY` | `100` | Concurrent virtual users. **The controlled variable** — this is the one to sweep. Also settable as an env var on the generator directly. |
| `DURATION` | `30s` | The measured window, *excluding* warmup. Asking for 30s of data gets 30s of data. |
| `WARMUP` | `10s` | Traffic discarded before measuring, so cold connection pools and a cold Go runtime stay out of the numbers. |
| `THINK` | `0` | Pause between one user's requests. See the warning below. |
| `TIMEOUT` | `10s` | Per-request timeout. If the report says the tail is censored, raise this. |
| `CORES` | `8` | Cores allocated to the stack; the denominator for the saturation figure. |
| `CORE_RANGE` | `0-7` | Label for those cores in the report text. Cosmetic. |
| `CEILING` | `14000` | Throughput ceiling for the headroom section, in req/s. |
| `RESULTS_DIR` | `results` | Where reports are written. |

### Why `THINK=0` matters

The Go harness defaults to `-think=1s`, which is right for simulating real users.
It is wrong for a capacity test: at one request per user per second, 200 users
offer 200 req/s regardless of how fast the service is, and `CONCURRENCY` stops
being a load control at all. `THINK=0` makes each user issue its next request as
soon as the last one returns, so the offered load rises with concurrency and the
service is what limits throughput.

If you set `THINK` non-zero, the run becomes a fixed-arrival-rate test and the
headroom section stops being meaningful — you will be measuring the number you
chose, not the number the service can do.

## What one run actually does

1. `docker compose up -d` for the six services under test.
2. Rebuilds the `loadgen` image, so edits to the harness are picked up.
3. Polls `GET /api/v1/health` until it answers. nginx lists the replicas in
   `depends_on` without a condition, so it can be accepting connections before
   any replica can answer; waiting on the actual endpoint is the only check that
   means anything.
4. Resolves the six services to container IDs and starts a background
   `docker stats` stream on the host, writing timestamped CPU samples to
   `results/<run>_cpu.csv`.
5. Runs the generator inside the compose network at the given concurrency,
   writing a structured summary to `results/<run>.json`.
6. Stops the collector — on every exit path, including a failed run or Ctrl-C.
7. Runs `cmd/loadreport`, which merges the summary and the CPU samples into
   `results/<run>.md`.

Three files land per run. The `.md` and `.json` are tracked in git — they are the
analysis. The `_cpu.csv` is gitignored raw input.

### Why CPU is collected on the host

`docker stats` reports a container's CPU as a percentage where **100% is one
fully busy core**. The six services under test are pinned to cores 0-7, so the
sum across them saturates at **800%**. The generator is pinned to cores 8-11 and
is deliberately excluded — including it would inflate the saturation figure for
cores it never touches. The script passes an explicit list of container IDs to
`docker stats` rather than a name filter, which is what guarantees the
generator's own run container cannot leak in.

Samples are intersected with the measured window before aggregating, so
saturation covers the same seconds as the throughput and latency figures rather
than being diluted by warmup.

The collector streams `docker stats` rather than calling it repeatedly with
`--no-stream`. A `--no-stream` call has to take two readings to compute a CPU
delta, so each one costs 3-4 seconds on Docker Desktop: a 30-second window would
land about seven samples and miss any peak narrower than four seconds. Streaming
gives roughly three readings a second. Each reading is stamped with a
millisecond-precision timestamp, because the report sums samples that share a
timestamp to get combined CPU — at whole-second precision two readings would land
in the same group and report double the real load.

## Reading the report

### Summary

Throughput counts every request that completed inside the measured window. The
p99 is over **all** requests, failures included.

### Tail latency

Two rows. **All requests** is the honest one — it includes failed and timed-out
requests at the latency they actually took. The accepted-only row is there for
comparison, but reading it alone is misleading in the dangerous direction: it
caps the tail at `TIMEOUT` no matter how bad things get, and lets the percentiles
*improve* under load as the slowest requests fail out of the set instead of being
counted.

If the report warns that latency is **censored**, the slowest request was sitting
at the timeout. p99.9 and max are then floors, not measurements. Re-run with a
larger `TIMEOUT`.

### Headroom

Two ceilings exist for this service, and they are nowhere near each other:

| Ceiling | Value | When it applies |
|---|---|---|
| General throughput | ~14,000 req/s | Request handling: nginx, the Go HTTP stack, the three replicas. No hashing, no database. |
| Login-specific | ~105 req/s | `POST /api/v1/auth/login`, where Argon2id saturates all cores at a tiny request rate. |

`make loadtest` drives `GET /api/v1/health`, so it always uses **the general
ceiling**, and the report says so explicitly. The login ceiling is roughly 130x
lower and applying it here would be nonsense — nothing in these runs hashes a
password.

Utilization is achieved ÷ ceiling. The report flags anything **over 50%**,
because the rule of thumb is to run at half of measured capacity: it leaves room
for a traffic spike, and with three replicas it means losing one still leaves the
other two able to carry the load.

### Error rate

A request counts as failed if it errored in transport **or** did not answer the
success status. The two are reported separately — a 502 and a timeout are both
failures with entirely different causes.

Availability is quoted in nines. A run with zero failures has infinite nines,
which is not a result, so the report gives the bound instead: N requests without
a failure cannot demonstrate more than about log10(N) nines however clean it
looked. Half a million clean requests is about 5.7 nines of evidence, not proof
of perfection.

### Saturation

Per-container averages and peaks, then a combined figure and what it is as a
percentage of the 8 allocated cores.

The combined figure sums per timestamp and *then* averages, rather than summing
each container's average. For the average those are the same; for the peak they
are not, because container peaks do not coincide — summing individual peaks would
invent a moment of load that never happened.

**This is the section that tells you whether the throughput number means
anything:**

| Saturation | What it means |
|---|---|
| ≥ 90% | The cores are saturated. Throughput is a real ceiling; more concurrency buys latency, not req/s. |
| 60–90% | Working hard but not pinned. There is probably some throughput left. |
| < 60% | The throughput figure is the load that was *offered*, not a capacity limit. Raise `CONCURRENCY` before concluding anything about capacity. |

## Running a sweep

One run is one concurrency level, by design. Sweep by invoking it repeatedly:

```bash
make loadtest CONCURRENCY=50 && make loadtest CONCURRENCY=100 && make loadtest CONCURRENCY=200 && make loadtest CONCURRENCY=500
```

Across the resulting reports, compare:

- **Throughput vs concurrency.** It rises, then flattens. The knee is capacity.
- **p99 vs concurrency.** Past the knee, throughput stops rising and p99 climbs
  instead — the queue is growing, not the service.
- **Saturation vs concurrency.** If throughput flattened while saturation is
  still well under 90%, the bottleneck is not CPU: look at connection limits,
  the nginx `keepalive` pool, or the generator itself.
- **Error rate.** Errors appearing as concurrency rises is the service shedding
  load. Note *which* kind — timeouts and resets mean different things.

## Troubleshooting

**`loadgen` appears in the CPU CSV.** The saturation figure is invalid — the
generator runs on cores 8-11 and is not part of what is being measured. Check
that `SERVICES` in `scripts/loadtest.sh` still lists only the six services under
test. Verify with:

```bash
grep -c loadgen results/loadtest_*_cpu.csv
```

**"Window alignment unavailable" in the saturation section.** Fewer than three
CPU polls landed inside the measured window, so the report fell back to the whole
collection period and says so. Usually clock skew between the Windows host
running the collector and the container clock the harness stamps. A very short
`DURATION` can also cause it — the collector polls roughly once a second, so a 3s
window is cutting it fine.

**"No CPU samples for this run."** The collector produced nothing. Throughput,
latency and error rate are unaffected and still valid; only saturation is
missing. Check that `docker stats` works by hand.

**Paths like `C:/Program Files/...` in a Docker error**, e.g. `exec: "C:/Program":
stat C:/Program: no such file or directory`. Git Bash rewrote a container-side
path into a Windows one. Run manual Docker commands through the wrapper, which
sources the fix first:

```bash
bash scripts/compose.sh run --rm --no-deps --entrypoint /loadreport loadgen -h
```

**`docker: unknown command: docker compose` from a Makefile target, while the
same command works at a prompt.** GNU Make on MSYS hands recipes an environment
stripped of the Windows variables, and the Docker CLI needs `%ProgramFiles%` to
locate its compose plugin. `go test` fails the same way, needing `%USERPROFILE%`
and `%LOCALAPPDATA%`. `scripts/win-env.sh` reconstructs all of them and is
sourced by every entry point — if you add a Makefile target that shells out to
docker or go, route it through `scripts/compose.sh` or source `win-env.sh`
rather than calling the tool directly.

**An orphaned `docker stats` process after Ctrl-C.** Should not happen — the
script traps `EXIT INT TERM` and reaps the collector. If you find one, kill it;
it is harmless but it holds the CSV open.

**The gateway never answers within 60s.** The run aborts rather than producing
numbers about a stack that is not up. Check `make ps` and `make logs`.

**Docker Desktop is not running.** Every command fails with
`open //./pipe/dockerDesktopLinuxEngine: The system cannot find the file
specified`. Start Docker Desktop and wait for the engine before retrying.

## What this does not measure

- **Login.** `make loadtest` drives the health endpoint only. Login is a
  completely different cost profile (Argon2id, ~105 req/s) and needs the
  generator's `-target=login` path, which also runs a rate-limiter phase. Run it
  by hand — see [`cmd/loadtest/README.md`](../cmd/loadtest/README.md).
- **Token validation.** The harness cannot drive PASETO validation yet: it
  discards login response bodies and keeps no per-user token state, so there is
  no token to present. Adding it is harness-side work, not a gateway change.
- **Anything above nginx.** All runs go through the compose network. Real-world
  TLS termination, internet latency and client behaviour are out of scope, which
  is the point — these numbers describe the service, not the path to it.
